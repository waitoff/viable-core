# Git как мозг: почему вашему ИИ-агенту нужен репозиторий, а не просто база данных

Когда мы строим мультиагентные системы, самая большая проблема — это координация. Агенты начинают мешать друг другу: один деплоит код, пока второй рефакторит базу данных, а третий в это время пишет анонс фичи, которая только что «сломалась». 

В классическом VSM (Viable System Model) за порядок отвечают **System 2** (Координация) и **System 3** (Управление). В Viable Core мы реализуем их через **Git-native подход**. 

Почему Git? Потому что это идеальный инструмент для управления состоянием, который инженеры используют десятилетиями. Если Git подходит для распределенных команд людей, он идеально подходит и для агентов.

## Провал Агента X: история о бесконечных циклах

Помните нашего Агента X? Он потратил $50 на токены, просто переписываясь сам с собой в бесконечном цикле. Почему это произошло? Потому что его «память» была эфемерной. Он видел только текущий контекст и не понимал, что делает одно и то же действие десятый раз.

Если бы Агент X работал в Git-native архитектуре, каждый его «шаг» был бы коммитом. 
1. Система 2 (светофор) увидела бы, что в ветку `thought-process` сыплются идентичные изменения.
2. Система 3 (ресурсный менеджер) заметила бы, что лимит токенов на эту задачу исчерпан.
3. Система мгновенно сделала бы `git reset`, откатив агента к моменту до начала психоза, и позвала бы человека.

## System 2: Светофор вместо менеджера

В Viable Core координация — это не «главный агент», который всеми командует. Это набор правил, реализованных через Git-hooks и файлы состояния.

Мы называем это **«светофорами»**. 
Пример: Агент-разработчик создает ветку `feature/auth`. Система 2 автоматически создает файл-мьютекс в репозитории. Если Агент-маркетолог пытается написать пост об этой фиче, он видит «красный свет»: *«Ветка feature/auth еще не прошла аудит S3*. Жди».*

Это не требует сложной логики диалогов между агентами. Они просто смотрят на состояние репозитория. Git становится «единым источником правды» (Single Source of Truth).

## System 3: Ресурсный менеджер и «Мягкий деплой»

S3 отвечает за то, чтобы агенты не сожрали ваш бюджет и не убили прод. В Git-native подходе это реализуется через **контроль диффов**.

Перед тем как агент внесет изменения в «память» или «код», S3* (аудитор) анализирует дифф:
- Сколько строк изменено? 
- Не нарушает ли это границы «аттрактора» (System 5)?
- Соответствует ли это текущему бюджету токенов?

Если агент-кодер вдруг решил переписать 200 файлов за один раз, S3 блокирует коммит: «Слишком большой объем изменений. Разбей на атомарные задачи». Это защищает систему от «галлюцинаторных взрывов», когда одна ошибка модели разносится по всему проекту.

## Главные фишки Git-native архитектуры

1. **Диффы вместо логов.** Вы не читаете тысячи строк чата. Вы смотрите `git diff`. Что агент изменил в своем плане? Что он добавил в список «побед»? Это наглядно и понятно.
2. **Путешествия во времени.** Если агент зашел в тупик, вы делаете `git checkout` на два часа назад. Агент «просыпается» в стабильном состоянии и пробует другой путь. Это дешевле и быстрее, чем пытаться «переубедить» его в чате.
3. **Параллельные миры.** Агент может запустить три разные стратегии решения задачи в трех разных ветках. S3 сравнит результаты (диффы и метрики) и выберет лучшую, сделав `merge`. 

## Итог

Git — это не просто хранилище кода. В Viable Core это **инфраструктура сознания**. 
System 2 использует его для координации (мьютексы и ветки), а System 3 — для контроля качества и ресурсов (аудит диффов).

Это превращает разработку агентов из «гадания на промптах» в нормальный инженерный процесс. Теперь у нас есть контроль, версионирование и возможность отката.
